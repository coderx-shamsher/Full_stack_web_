Yes. For **TypeScript interviews**, you should not learn only `any`, `unknown`, and `never`. There are a few other special types/keywords that are important enough that I'll add them to your interview roadmap.

# TypeScript Special Types — Complete Interview Set

The core ones are:

```text
any
unknown
never
void
undefined
null
object
{}
```

And then there are important type-system keywords/operators:

```text
keyof
typeof
in
is
as
satisfies
```

Let's understand them one by one.

---

# 1. `any` 🔴

### Meaning

> "TypeScript, stop checking this value."

```ts
let value: any = "hello";

value = 100;
value = true;
value.foo.bar();
```

TypeScript generally won't protect you.

### Example

```ts
function print(value: any) {
  console.log(value.name);
}
```

You can pass anything:

```ts
print("hello");
print(123);
print({});
```

### Use?

Prefer to **avoid `any`**.

```text
any
 ↓
No type safety
 ↓
Potential runtime errors
```

---

# 2. `unknown` 🟢

### Meaning

> "I don't know the type yet, so verify it before using it."

```ts
let value: unknown = "hello";
```

This is NOT allowed:

```ts
value.toUpperCase();
```

❌

You need to narrow it:

```ts
if (typeof value === "string") {
  value.toUpperCase();
}
```

### Best use cases

* API data
* `JSON.parse()`
* external libraries
* user input
* errors

```ts
const data: unknown = await response.json();
```

Think:

```text
any     → "Trust me."
unknown → "Prove it."
```

---

# 3. `never` 🔥

### Meaning

> **A value that can never occur.**

Most commonly, a function that never successfully returns.

```ts
function throwError(message: string): never {
  throw new Error(message);
}
```

This function never reaches a normal return.

Another example:

```ts
function infiniteLoop(): never {
  while (true) {
    console.log("running");
  }
}
```

It doesn't finish.

---

## `never` is VERY useful with discriminated unions

```ts
type Status =
  | "loading"
  | "success"
  | "error";
```

You can enforce exhaustive handling:

```ts
function assertNever(value: never): never {
  throw new Error("Unexpected value");
}

function handleStatus(status: Status) {
  switch (status) {
    case "loading":
      return "Loading";

    case "success":
      return "Success";

    case "error":
      return "Error";

    default:
      return assertNever(status);
  }
}
```

If later you add:

```ts
type Status =
  | "loading"
  | "success"
  | "error"
  | "cancelled";
```

TypeScript can tell you that `"cancelled"` wasn't handled.

**Interview importance: ⭐⭐⭐⭐⭐**

---

# 4. `void`

This one is commonly confused with `never`.

`void` means:

> "This function doesn't return a useful value."

```ts
function logMessage(): void {
  console.log("Hello");
}
```

The function finishes.

```text
void
 ↓
function executes
 ↓
function finishes
 ↓
no useful return value
```

Compare:

```ts
function log(): void {
  console.log("hello");
}
```

vs

```ts
function fail(): never {
  throw new Error("Failed");
}
```

### Key difference

```text
void  → returns normally, but no value
never → never returns normally
```

---

# 5. `undefined`

`undefined` is an actual JavaScript value.

```ts
let value: undefined;

value = undefined;
```

A function can return it:

```ts
function findUser(): User | undefined {
  // maybe user exists
  return undefined;
}
```

Then:

```ts
const user = findUser();

if (user) {
  console.log(user.name);
}
```

This is extremely common when something **may not exist**.

---

# 6. `null`

`null` is also an actual JavaScript value.

It commonly represents:

> "There is intentionally no value."

```ts
let user: User | null = null;
```

Later:

```ts
user = {
  id: 1,
  name: "Steve"
};
```

In React you'll see this constantly:

```tsx
const [user, setUser] = useState<User | null>(null);
```

Initially:

```text
user → null
```

After API request:

```text
user → User
```

So:

```ts
if (user) {
  console.log(user.name);
}
```

---

# 7. `object`

`object` means a **non-primitive value**.

For example:

```ts
let value: object;

value = {};
value = [];
value = () => {};
```

But:

```ts
value = "hello";
value = 123;
value = true;
```

❌

Be careful: `object` is usually too broad if you actually care about the object's structure.

Instead of:

```ts
function process(user: object) {}
```

prefer:

```ts
interface User {
  id: number;
  name: string;
}

function process(user: User) {}
```

---

# 8. `{}` — Don't Confuse This With "Empty Object"

This is a common interview trap.

Many beginners think:

```ts
let value: {};
```

means:

> "value must be an empty object."

❌ Not exactly.

In TypeScript, `{}` is essentially a very broad non-nullish type.

For example, many values can satisfy it:

```ts
let value: {};

value = "hello";
value = 123;
value = true;
value = [];
value = {};
```

So **don't use `{}` when you mean "an object with no properties."**

If you genuinely want an object with no known properties, there are better patterns depending on the situation.

---

# 9. `keyof` ⭐⭐⭐⭐⭐

This isn't a type itself; it's a **type operator**.

Suppose:

```ts
interface User {
  id: number;
  name: string;
  email: string;
}
```

Then:

```ts
type UserKeys = keyof User;
```

becomes:

```ts
type UserKeys = "id" | "name" | "email";
```

Think:

```text
keyof User
    ↓
"What are the keys of User?"
    ↓
"id" | "name" | "email"
```

This is extremely important for generics.

```ts
function getProperty<T, K extends keyof T>(
  obj: T,
  key: K
) {
  return obj[key];
}
```

Now:

```ts
const user = {
  id: 1,
  name: "Steve"
};

getProperty(user, "name"); // ✅
getProperty(user, "id");   // ✅
getProperty(user, "email"); // ❌
```

This is a **high-priority interview topic**.

---

# 10. `typeof`

You already know JavaScript:

```ts
typeof value
```

But TypeScript gives `typeof` another powerful use.

You can use it to get the **type of an existing variable**.

```ts
const user = {
  name: "Steve",
  age: 22
};

type User = typeof user;
```

TypeScript creates essentially:

```ts
type User = {
  name: string;
  age: number;
};
```

This is very useful when you want to derive a type from an existing value.

---

# 11. `in`

You saw this with type narrowing.

```ts
type Admin = {
  permissions: string[];
};

type Customer = {
  orders: number;
};

function process(user: Admin | Customer) {
  if ("permissions" in user) {
    console.log(user.permissions);
  } else {
    console.log(user.orders);
  }
}
```

The `in` check tells TypeScript which object type you're dealing with.

---

# 12. `instanceof`

Used to check whether something is an instance of a class.

```ts
function handleError(error: unknown) {
  if (error instanceof Error) {
    console.log(error.message);
  }
}
```

Before:

```text
error → unknown
```

After:

```text
error instanceof Error
        ↓
error → Error
```

---

# 13. `is` ⭐⭐⭐⭐

This is used when creating **custom type guards**.

```ts
interface User {
  name: string;
  age: number;
}

function isUser(value: unknown): value is User {
  return (
    typeof value === "object" &&
    value !== null &&
    "name" in value &&
    "age" in value
  );
}
```

The important part:

```ts
value is User
```

means:

> If this function returns `true`, TypeScript can treat `value` as `User`.

Then:

```ts
const data: unknown = getData();

if (isUser(data)) {
  console.log(data.name);
}
```

---

# 14. `as` — Type Assertion

`as` tells TypeScript:

> "Treat this value as this type."

```ts
const value: unknown = "Hello";

const message = value as string;

console.log(message.toUpperCase());
```

But remember:

> ⚠️ `as` does **not** perform runtime validation.

This:

```ts
const value: unknown = 123;

const message = value as string;
```

doesn't magically convert `123` into a string.

You're just telling TypeScript to trust you.

---

# 15. `satisfies` ⭐⭐⭐⭐⭐

This is a **modern TypeScript feature** and worth knowing for interviews.

Suppose:

```ts
type Config = {
  mode: "dark" | "light";
  fontSize: number;
};
```

You could do:

```ts
const config: Config = {
  mode: "dark",
  fontSize: 16
};
```

But `satisfies` lets you **validate the shape while preserving the more specific inferred type**.

```ts
const config = {
  mode: "dark",
  fontSize: 16
} satisfies Config;
```

Think:

```text
as
 ↓
"Trust me, this is Config."

satisfies
 ↓
"Check that this matches Config,
but keep the specific inferred information."
```

This is especially useful for configuration objects, route definitions, maps, etc.

---

# 16. `readonly`

Another important keyword.

```ts
type User = {
  readonly id: number;
  name: string;
};
```

Now:

```ts
const user: User = {
  id: 1,
  name: "Steve"
};

user.name = "Alex"; // ✅

user.id = 2; // ❌
```

`readonly` prevents assignment through that property.

---

# 17. `const` vs `readonly`

Don't confuse these.

```ts
const user = {
  name: "Steve"
};

user.name = "Alex"; // ✅
```

`const` prevents reassigning the variable:

```ts
user = {}; // ❌
```

But it doesn't make the object's properties immutable.

`readonly` does:

```ts
type User = {
  readonly name: string;
};
```

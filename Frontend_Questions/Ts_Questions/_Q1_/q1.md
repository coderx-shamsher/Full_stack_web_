this is a **very common TypeScript frontend interview question**. The key is not to memorize “interface vs type”; understand **what problem each one solves**.

# Question ===>  `interface` vs `type` in TypeScript

Both can describe the **shape of data**.

For example, both can represent a user:

```ts
interface User {
  name: string;
  age: number;
}
```

and:

```ts
type User = {
  name: string;
  age: number;
};
```

Both work.

So the real interview question is:

> **If both can describe an object, why do we have both?**

---

# 1. `interface`

An `interface` is mainly designed to describe the **structure/contract of an object**.

```ts
interface User {
  name: string;
  age: number;
}

const user: User = {
  name: "Steve",
  age: 22
};
```

Think:

> **Interface = "This object should have these properties."**

### Frontend example

Suppose your API returns users:

```ts
interface User {
  id: number;
  name: string;
  email: string;
}
```

Then:

```ts
function UserCard({ user }: { user: User }) {
  return (
    <div>
      <h2>{user.name}</h2>
      <p>{user.email}</p>
    </div>
  );
}
```

This is a very natural use of `interface`.

---

# 2. `type`

`type` is more flexible.

It can describe objects:

```ts
type User = {
  name: string;
  age: number;
};
```

But it can also describe things that aren't just object shapes.

### Union

```ts
type Status = "loading" | "success" | "error";
```

Now:

```ts
let status: Status;

status = "loading"; // ✅
status = "success"; // ✅
status = "error";   // ✅

status = "pending"; // ❌
```

This is one of the biggest reasons to use `type`.

---

# 3. Type can describe primitive aliases

```ts
type UserId = string;

type Age = number;
```

Then:

```ts
const id: UserId = "user_123";
const age: Age = 22;
```

You generally don't use an interface for this.

---

# 4. Type can describe tuples

```ts
type Coordinates = [number, number];

const location: Coordinates = [31.63, 74.87];
```

Again, `type` is the natural choice.

---

# 5. Type can describe functions

```ts
type Add = (a: number, b: number) => number;

const add: Add = (a, b) => {
  return a + b;
};
```

This is another useful `type` use case.

---

# 6. Interfaces can be extended

Suppose:

```ts
interface User {
  name: string;
  age: number;
}
```

You can extend it:

```ts
interface Admin extends User {
  permissions: string[];
}
```

Now:

```ts
const admin: Admin = {
  name: "Steve",
  age: 22,
  permissions: ["delete", "edit"]
};
```

Conceptually:

```text
User
 ├── name
 └── age

      ↓ extends

Admin
 ├── name
 ├── age
 └── permissions
```

This is very useful when modeling related objects.

---

# 7. Types can also be combined

With `type`, you commonly use intersections:

```ts
type User = {
  name: string;
  age: number;
};

type Admin = User & {
  permissions: string[];
};
```

This creates:

```ts
type Admin = {
  name: string;
  age: number;
  permissions: string[];
};
```

So:

```text
interface → extends
type      → &
```

That's a useful interview-level distinction.

---

# 8. The BIG Difference: Declaration Merging ⭐

This is something interviewers sometimes ask.

Interfaces can be **re-opened**.

```ts
interface User {
  name: string;
}

interface User {
  age: number;
}
```

TypeScript combines them.

Effectively:

```ts
interface User {
  name: string;
  age: number;
}
```

This is called:

> **Declaration merging**

---

With `type`:

```ts
type User = {
  name: string;
};

type User = {
  age: number;
};
```

❌ Error.

You cannot declare the same type alias twice in the same scope.

---

# 9. Why Does Declaration Merging Matter?

This is especially relevant to **libraries and framework typings**.

For example, TypeScript allows interfaces to be extended/augmented by other code.

You may encounter patterns like:

```ts
interface Window {
  myCustomProperty: string;
}
```

This can extend the existing `Window` interface.

That's one reason interfaces are heavily used in TypeScript libraries.

---

# 10. `interface` Doesn't Handle Unions Like `type`

This works:

```ts
type Status =
  | "loading"
  | "success"
  | "error";
```

You can't directly do the same thing with an interface.

That's because `type` aliases can represent **unions**.

This is very useful in frontend development.

For example:

```ts
type ButtonVariant =
  | "primary"
  | "secondary"
  | "danger";
```

Then:

```tsx
function Button({
  variant
}: {
  variant: ButtonVariant;
}) {
  // ...
}
```

Now TypeScript prevents:

```tsx
<Button variant="random" />
```

---

# 11. Discriminated Unions 🔥

This is where `type` becomes extremely powerful.

Imagine an API request state:

```ts
type RequestState =
  | {
      status: "loading";
    }
  | {
      status: "success";
      data: User[];
    }
  | {
      status: "error";
      error: string;
    };
```

Now:

```ts
function render(state: RequestState) {
  if (state.status === "loading") {
    return "Loading...";
  }

  if (state.status === "success") {
    return state.data;
  }

  return state.error;
}
```

TypeScript understands which properties are available based on `status`.

This pattern is **extremely useful in frontend applications**.

---

# 12. Can `interface` extend a `type`?

Sometimes yes.

For example:

```ts
type User = {
  name: string;
  age: number;
};

interface Admin extends User {
  permissions: string[];
}
```

This can work when the type has an object-like statically known shape.

But interfaces have restrictions around what they can extend, while `type` intersections are generally more flexible.

---

# 13. Can a `type` use an `interface`?

Absolutely.

```ts
interface User {
  name: string;
}

type Admin = User & {
  permissions: string[];
};
```

So they aren't isolated systems.

You can combine them.

---

# 14. Practical Frontend Examples

## API data → `interface`

```ts
interface Product {
  id: number;
  title: string;
  price: number;
  image: string;
}
```

Good choice because you're describing an object's structure.

---

## React props → either works

```ts
interface ButtonProps {
  title: string;
  disabled?: boolean;
}
```

Then:

```tsx
function Button({
  title,
  disabled
}: ButtonProps) {
  return (
    <button disabled={disabled}>
      {title}
    </button>
  );
}
```

You could also use:

```ts
type ButtonProps = {
  title: string;
  disabled?: boolean;
};
```

Both are valid.

---

# 15. React Event Types → Usually `type` / direct types

For example:

```tsx
const handleChange = (
  event: React.ChangeEvent<HTMLInputElement>
) => {
  console.log(event.target.value);
};
```

Here you're using an existing type supplied by React.

---

# 16. When Should YOU Use Which?

Here's the practical rule I'd recommend for interviews and real projects:

| Situation                  | Prefer                |
| -------------------------- | --------------------- |
| Object shape               | `interface`           |
| API response model         | `interface`           |
| Component props            | `interface` or `type` |
| Class contract             | `interface`           |
| Extending object contracts | `interface`           |
| Union types                | `type`                |
| Literal unions             | `type`                |
| Tuples                     | `type`                |
| Function type              | `type`                |
| Complex combinations       | `type`                |
| Discriminated unions       | `type`                |
| Need declaration merging   | `interface`           |

---

# ⭐ My Practical Rule

If I'm writing:

```ts
interface User {
  id: number;
  name: string;
}
```

I'm thinking:

> **"This is an object contract."**

If I'm writing:

```ts
type Status = "idle" | "loading" | "success" | "error";
```

I'm thinking:

> **"This is a type definition/composition."**

That's the easiest mental model.

---

# 🔥 Interview Answer

If interviewer asks:

> **"What's the difference between interface and type in TypeScript?"**

Don't give a huge answer. Say:

> "`interface` and `type` can both describe object shapes, but interfaces are primarily designed for object contracts and support features like `extends` and declaration merging. Type aliases are more flexible because they can represent unions, intersections, tuples, primitive aliases, and function types. In practice, I usually prefer interfaces for extendable object models such as API entities or class contracts, and types when I need unions, intersections, or other type compositions."

That's a **strong interview answer**.

---

# 🧠 One Important Interview Trap

Don't say:

> ❌ "`interface` is for objects and `type` is for everything else."

That's **too simplistic and technically wrong**.

This is perfectly valid:

```ts
type User = {
  id: number;
  name: string;
};
```

And this is perfectly valid:

```ts
interface User {
  id: number;
  name: string;
}
```

The real difference is **capabilities and intent**, not simply "object vs non-object."

### Remember this:

```text
              TypeScript
                  │
       ┌──────────┴──────────┐
       ↓                     ↓
   interface               type
       │                     │
 object contracts       type composition
       │                     │
   extends              unions
   merging              intersections
   class contracts       tuples
                         functions
                         literals
```

For frontend interviews, after this topic, the next highly connected TypeScript topics are **`any` vs `unknown` vs `never` → generics → utility types → type narrowing → type guards → discriminated unions**.
